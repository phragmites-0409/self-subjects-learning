# 1. 本轮选型结论

**本轮（单机、单人、本地网页版）使用 SQLite，保持现有实现。** 这不是"先凑合"，而是该场景下的最优解。

## 1.1 理由

| # | 理由 | 说明 |
|---|---|---|
| 1 | 零运维 | 无服务进程、无端口、无账号、无版本升级；打开文件即用，完全符合"先保证本地能跑" |
| 2 | 备份即复制 | 单文件备份（`VACUUM INTO` 或 checkpoint 后复制），与 `data/objects` 一起打包即可；Postgres 需 `pg_dump` 并保证两份对齐 |
| 3 | 现有资产完全对齐 | 63 个后端测试、WAL/外键/`busy_timeout` 配置、SQLAlchemy 2 + Alembic 均围绕它运行 |
| 4 | 大字段已外置 | 解析正文与对话走压缩对象、图片与 PDF 走文件系统，DB 只存元数据，增长极慢 |
| 5 | 数据量远未触顶 | 见 §1.2 估算，百万行以内、库体积数十至数百 MB，而 SQLite 容量上限在 TB 级 |
| 6 | 写并发不是瓶颈 | 单人使用 + 进程内调度，写操作天然低频；真正的瓶颈只可能来自多进程 |

## 1.2 数据量估算（按 3 年使用）

| 数据 | 估算行数 | 备注 |
|---|---|---|
| 单词 + 义项 + 个人别名 | ~1.5 万 | 3500 词 × 平均 2–3 义项，最大的一块 |
| 题目 + 题目版本 | ~1.5 万 | 按每天 5 题、3 年计 |
| 错题条目 + 复盘 + 过手事件 | ~10 万 | 长期累积 |
| 每日任务 + 任务条目 + 日清/周清 | ~10 万 | 每天数十行 |
| 知识库节点 + 内容索引 + 关联 | ~1 万 | 含外部导入 |
| 批改提交 + 判定条目 | ~2 万 | 按每天 2 次批改计 |

**结论**：总量在百万行以内。SQLite 的容量与读性能都不是问题，唯一需要管理的资源是**写锁**。

## 1.3 已排除的选项

| 选项 | 排除理由 |
|---|---|
| PostgreSQL | 本轮收益为零、成本为正：需安装/Docker、备份策略、启动依赖；而**本轮是单机单人**，云端的实施时点与"是否保留本地端"仍未定，现在换引擎等于为未定的未来付费（且换引擎并非上云的主要成本，见 §5） |
| MySQL / MariaDB | 相对 Postgres 无优势，同样有运维成本 |
| DuckDB | 分析型引擎，写并发与在线事务能力不适配本项目的交互式写入 |
| MongoDB 等文档库 | 与现有 SQLAlchemy + Alembic + 关系模型资产冲突，且丢失外键与约束保护 |
| 内存数据库 | 不满足持久化要求 |
| libSQL / Turso | **不作本轮选择，但作为上云路径保留**（见 §5 路径 2） |

# 2. 配套硬约束

选 SQLite 不是无条件的，以下四条是本轮的实施红线。**第 1 条已与你确认接受。**

## 2.1 必须单进程运行（红线）

- `uvicorn` **单 worker**；调度器与后台 Job worker 一律**进程内**（asyncio 任务或线程池）。
- 禁止：多 worker（`--workers N>1`）、多进程写库、把调度器拆成独立进程或 Windows 服务。
- 原因：SQLite 是单写者模型；多进程写同一文件会出现 `database is locked`。现有配置只设了 `busy_timeout=5000`（[session.py:26](backend/app/db/session.py#L26)），它能缓解偶发争用，但挡不住结构性并发。
- 这恰好与本轮"推送机制从简、不引入外部服务"的要求一致。

## 2.2 DB 只存元数据

- 完整解析、对话、导入内容 → gzip 压缩对象；图片、PDF、手写原件、作答原件 → 文件系统。
- 保持现有 `Asset` + `storage_key` + `sha256` 模式，不在库里存二进制或重复正文。

## 2.3 AI 调用与长任务不进数据库事务

- 网络调用、PDF 生成、批量批改、自动组卷都在事务外执行，事务只用于短提交。
- 改造 Job 体系（P0）时必须继续保持，避免长写锁阻塞整个应用。

## 2.4 Alembic 一律走 batch 模式

- SQLite 的 `ALTER TABLE` 能力弱：改约束、删列、改类型都需要重建表。
- 因此所有 revision 使用 `render_as_batch=True`（`env.py` 配置）或显式 `batch_alter_table`。
- 这是对主文档 §5.5"迁移策略"的补充实施细节，属于 P0 范围。

# 3. SQLite 的真实边界（诚实记录）

| 边界 | 表现 | 应对 |
|---|---|---|
| 单写者 | 写操作串行；长写事务阻塞所有写 | §2.3；写入批量化、避免逐条提交 |
| 多进程冲突 | 多 worker/多进程写同一文件报锁错误 | §2.1 单进程红线 |
| `ALTER` 能力弱 | 改约束/删列需重建表 | §2.4 batch 模式 |
| 无行级权限（RLS） | 多用户隔离只能应用层实现 | 未来上云时由 Postgres RLS 或应用层过滤承担 |
| 中文全文检索弱 | FTS5 的 `unicode61` 对中文不分词 | 先 `LIKE` + 索引；需要时再引入分词方案 |
| 方言函数 | 现有 3 处 `json_each` 检索 JSON 数组 | 已在风险清单（§6 第 1 条） |
| 时区类型被忽略 | `DateTime(timezone=True)` 在 SQLite 不保留偏移 | 已在风险清单（§6 第 7 条） |
| 手写迁移 | [models.py:397-561](backend/app/db/models.py#L397-L561) 为 SQLite 专用表重建 | 引入 Alembic 时改为一次性 data migration |

# 4. 何时必须更换（触发条件）

出现以下任一情况，就应把数据库换成服务型（Postgres 系）：

1. 需要**多进程/多实例/多机**部署，或云端需要并发写；
2. 需要**行级权限（RLS）**做多用户隔离；
3. 需要**服务端中文全文检索**（`pg_trgm` / `zhparser` 明显强于 SQLite）；
4. 题库进入**百万题量级**并需要复杂聚合统计（考情统计的进阶形态）；
5. 云端形态确定为 Supabase 系（其数据库即 Postgres）。

在此之前，SQLite 都是更优选择。

# 5. 上云演进路径

**关键判断：换不换引擎，都不是上云的主要成本。** 即使今天就用 Postgres，上云仍然必须做：对象存储改云、账号与权限、多用户数据隔离、并发模型改造、`json_each` 重写、手写迁移替换。这些的工作量与"把 SQLite 数据导入 Postgres"相比是数量级的差别。

| 路径 | 做法 | 主要改动 | 代价 |
|---|---|---|---|
| **1. 走 Supabase 系** | SQLite → Postgres 迁移；Supabase 提供 Postgres + Storage（+ Auth 可选） | ①`json_each` 三处重写；②手写迁移替换；③`connect_args`/PRAGMA 按方言分支；④`database_url` 可配置化；⑤对象存储换实现（现有 9 处直接 `new LocalFilesystemContentStore()`）；⑥加身份列与 RLS | 改动集中但明确，是本文件风险清单的主要来源 |
| **2. 保留 SQLite 上云** | 换 libSQL / Turso（SQLite 协议网络化） | SQL 几乎不改；补齐网络化连接与鉴权 | 用不上 Supabase 的 Auth/Storage/Realtime 生态；中文检索与 RLS 仍受限 |
| **3. 双存储** | 本地为主 + 云端为辅 | 需补：`revision`（写入自增）、软删除墓碑（`deleted_at`）、变更日志/outbox、冲突策略、对象镜像与去重 | 最贵；本轮未加这些字段，将来要补 |

**当前建议**：先按路径 1 或 2 的可能性组织，等云端形态确定后再实施；本轮不做任何可移植性改造（见 §6）。

## 7.1 已确定的云端形态

| 维度 | 结论 |
|---|---|
| 账号 | **每人一个账号登录**；本轮的 `accounts` / `sessions` 与 `owner_id` 直接演进，届时把凭据校验换成云 Auth（Supabase Auth 或自建 JWT）即可，**业务层不动** |
| 数据归属 | **基础功能的数据每人分开存储**：题目与解析、知识库、错题本、单词、计划等全部按 `owner_id` 隔离 |
| 跨设备 | **部分内容需放在云端以便跨设备查阅**；范围**暂按**"除临时文件、日志、备份外的全部业务数据"设计，但**明确标注为暂不确定——正式实施前必须先确认**（见 §9 第 6 条） |
| 新增功能 | **论坛**（见 §7.2） |
| 对象存储 | 本轮只本地；云端**原件不进数据库**，走独立对象存储或"宿主设备中转"（见 §10） |
| 使用规模 | **预计 10 人以上**：必须启用 RLS 或应用层强制 `owner_id` 过滤（二者选一，不能都不做），并注意连接池与配额监控（见 §10.6） |
| 容量约束 | 云端数据库配额有限（如 Supabase 5 GB）：**元数据够用、图片原件必须外置**（见 §10.1） |
| 本地与云端 | 是否保留本地端、是否需要双向同步**仍未定** |

## 7.2 论坛设计（本轮不实施）

**定位**：面向登录用户的公共讨论区，是**云端功能**——单机版没有他人，做论坛没有意义，因此本轮只在文档中设计。

| 维度 | 设计要点 |
|---|---|
| 位置与隔离 | 论坛是**独立的公共区**，与私人库彻底分离（不同表、不同 `owner_id` 语义）；届时顶层板块可能从 5 个变为 6 个 |
| 帖子类型 | 讨论帖 / 题目求助 / 方法分享；可带"题型 / 知识点"标签，但**引用云端公共知识树，不引用他人的私人节点** |
| **内容流通方式** | **分享 = 生成一份快照复制到公共区**，而非引用私人库记录。理由：私人数据随时可改可删，论坛内容必须自洽可存续；同时避免权限穿透 |
| 可流通内容 | 题目与解析、题型方法整理、知识条目、作文素材等**学习内容** |
| **隐私红线（禁止流通）** | **手写原件、作答原件、批改结果、错题本记录、日清周清与计划、单词学习进度、对话记录**——一律不得进入论坛 |
| 权限 | 浏览可公开或需登录；发帖/回复需登录；自己的帖子可编辑删除；需具备举报与管理员隐藏能力 |
| 与同步的关系 | 论坛数据本就生在云端，**不参与本地→云的单向备份**，也不与私人库混存 |
| 实施前提 | 需先确定云端形态（§7.1）与账号落地方式；**本轮不实现** |

# 9. 待定项（需在进入上云阶段前明确）

1. 云端形态：**是否保留本地端**（纯云端 / 云端 + 本地，见 §7.1）。
2. 双存储是否需要真双向同步（决定是否现在补同步元数据）。
3. 账号体系引入时点 —— **已解决**：本轮落地账号与 `owner_id`（见 §7.1）。
4. AI Key 与设置是否按账号隔离。
5. 对象存储是否上云（含手写原件与作答原件的隐私考虑）。
6. **跨设备查阅的范围**（暂按"除临时/日志/备份外的全部业务数据"设计）—— **正式实施前必须先确认**。
7. 论坛的上线时机与内容范围（§7.2）；是否需要一棵**公共知识树**，以及它与私人知识树的关系。
8. **对象存储后端的选择**：独立对象存储 / 宿主设备中转 / 混合，以及分层驱逐策略（见 §10）。
9. **Supabase 配额的具体口径**：数据库、Storage、出网流量分别是多少，是免费档还是 Pro 档——这直接决定 §10 选哪个方案。

# 10. 数据架构与 5 GB 约束下的分层存储

## 10.1 先算清楚：什么占空间

| 类别 | 单人估算 | 10 人估算 | 说明 |
|---|---|---|---|
| 元数据（题目与版本索引、知识树、标记、任务、计划、单词） | < 100 MB | **< 1 GB** | 纯结构化行；SQLite 与 Postgres 都很小 |
| 文本内容（解析、对话、归档条目的 gzip） | 100–200 MB | 1–2 GB | 约 5000 题 × 20–40 KB |
| **图片原件**（题干图、答案图、手写原件、作答照片） | **1–2.5 GB** | **10–25 GB** | 已压缩为 WebP，仍约 200–500 KB/张 |
| 缩略图 | ~100 MB | ~1 GB | 约 20 KB/张 |
| 生成的 PDF | 几十 KB–几 MB/份 | 视产量 | 试卷导出 |

**结论：瓶颈是图片原件，不是数据库。**

- 5 GB 用来放**元数据 + 缩略图 + 文本内容**是**绰绰有余**的（10 人合计约 2–4 GB）；
- 把原图也塞进去，**两三个人的量就会撑爆**。

> **两条必须先确认/必须遵守的前提**
> 1. **Supabase 的配额是分开计的**（数据库大小、Storage 大小、出网流量各有额度）。你说的 5 GB 是其中哪一项、免费档还是 Pro 档，会直接决定选哪个方案 —— 请先查清（已列入 §9 第 9 条）。
> 2. **图片永远不进数据库表**（无论 SQLite 还是 Postgres）。这是本设计从第一天起就定的原则。

## 10.2 三种可选架构

### 方案 A：元数据上云 + 原件留"宿主设备"，云端只做中转（你的设想）

- **云端**：账号、元数据、缩略图、文本内容 → Postgres + 少量 Storage
- **本地**：原图 / PDF / 手写原件 / 答案原件放在**我指定的目录**（通常是那台常开的电脑）
- **跨设备取件**：我在新设备点"取原图" → 云端下发取件请求 → **宿主设备上的常驻代理**把对象上传到**临时桶** → 我下载 → 临时对象按 **TTL 自动删除**
- 优点：5 GB 完全够用；**原件不出私域**（隐私最好）
- **必须解决的三个问题**：
  1. **宿主机离线就取不到** → 降级：最近使用过的对象在云端保留副本（LRU 热缓存，配额内）
  2. **需要常驻代理** → 一台设备上跑一个本地小服务，负责监听取件请求、上传、回报
  3. **一致性** → 内容寻址（`sha256`）天然防错；**删除云端副本前必须先确认本地副本存在**

### 方案 B：热 / 温 / 冷分层（不依赖某台设备常开）

- **热（云端）**：最近 N 天 / 最近 M 题 / 收藏与重点题的原图 + 全部缩略图 + 全部文本
- **冷（本地或独立存储）**：历史原图
- 云端按配额自动**驱逐**到冷层，驱逐前先确认冷层副本存在
- 优点：常用数据永远可用，不依赖宿主机
- 缺点：驱逐/恢复逻辑复杂；"上周看过的那张图"可能已被驱逐，需要等待恢复

### 方案 C：对象存储与数据库分开（最省事）

- **Supabase 只跑 Postgres（元数据）**；**对象走独立的便宜对象存储**（Cloudflare R2 / Backblaze B2 / 阿里 OSS 等，10 GB 级几乎免费）
- 优点：彻底绕开 5 GB；架构最简单；跨设备体验最好（对象始终在线）
- 缺点：多一个服务商；原件离开私域（隐私需接受）

## 10.3 推荐

**C + B 的组合，A 作为可选降级**：

1. **元数据**留在 Supabase Postgres（10 人 < 1 GB，非常安全）；
2. **对象**默认放独立对象存储（C），并按热/温分层（B）控制成本；
3. 若不愿原件出私域，把对象层切换为**方案 A 的宿主设备中转**。

> **因为 `ContentStore` 是抽象接口，上面三种只是不同实现** —— 这正是本轮必须把它收敛为依赖注入的原因。

## 10.4 为分层预留的字段（本轮就加，零运行代价）

| 字段 | 位置 | 作用 |
|---|---|---|
| `storage_tier` | `assets` | `local`（只在本地）/ `cloud`（已在云端）/ `both`（两处都有，可安全驱逐云端） |
| `sha256` | `assets`（已有） | 内容寻址：跨设备、跨层校验一致性 |
| `owner_id` | 全部业务表 | 分账号隔离的地基 |
| `revision` / `updated_at` / `deleted_at` | 全部业务表 | 同步与冲突判定的地基（真双向同步时必需） |
| `origin_device_id` | `assets`（可选） | 记录原件最初在哪台设备，便于取件 |

**这些字段本轮只有"写入值"的开销**：不写同步代码、不做分层调度，但将来**不必再改表结构**。

## 10.5 论坛（公共区）与私人库的边界

沿用 §7.2：论坛是云端公共区，**分享 = 快照复制**。额外要注意一点：

> **快照里的图片必须复制到公共区**。否则会出现"作者清掉本地原件后，论坛帖子裂图"——公共区的内容必须自洽、可独立存续。

## 10.6 10+ 人规模的额外考虑

| 项 | 说明 |
|---|---|
| 连接数 | 云端连接池有限：应用侧用连接池（PgBouncer / SQLAlchemy pool），不要每请求新建连接 |
| 行级权限 | 10+ 人**必须**启用 RLS，或由应用层强制 `owner_id` 过滤；**不能两者都不做** |
| 备份 | 数据库备份由 Supabase 承担；**对象层的备份与保留要自己定** |
| 配额监控 | 定期统计 数据库 / Storage / 出网 用量，接近阈值先告警（设置页或脚本） |
